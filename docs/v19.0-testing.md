# Jenkins v19 acceptance

## Source decision

Debian Trixie does not package the Jenkins controller. The appliance installs
Jenkins 2.568.2 from the official Jenkins LTS Debian repository and uses
OpenJDK 21 from Debian Trixie. Jenkins 2.555.1 and newer requires Java 21 or
25, and the project tests this LTS line with both versions.

The selected package and evidence are:

- Jenkins version `2.568.2`;
- repository key fingerprint
  `5E386EADB55F01504CAE8BCF7198F4B714ABFC68`;
- repository key SHA-256
  `d3b7e4096fed593eebdba3a2554c8cb9aafebe736910584e69e924b143e7b3d4`;
- package SHA-256
  `abaa015c3a39a8182eed136333d6d0ba055564df37584e699cc9693ad64ad7d5`.

The build installs plugins through Jenkins' own CLI after validating signed
update-center metadata from a mirror in the Jenkins distribution network. It
requires SHA-256 metadata for every requested plugin before installation, then
restores the canonical Jenkins update-center URL before sealing the appliance.
The focused job test requires the installed Git, Subversion, Pipeline SCM,
mail, and JUnit plugins.

During the image build, Jenkins starts with the package-supported systemd
`JAVA_OPTS` override. Java URL connections have a 15-second connect timeout and
a 30-second read timeout, so an unresponsive update endpoint cannot hold
SetupWizard indefinitely. The build removes this temporary override before
sealing; ordinary appliance traffic retains the package defaults.

## Loop accounting

Product loops 1 through 5 fixed Apache TLS setup, CLI JAR validation, Jenkins
root URL ordering, and the ineffective startup retry. Product loop 6 of 6 adds
the required update-center readiness boundary. Extending that candidate's
measured startup budget remains a refinement of loop 6, not a seventh product
loop. Test-only JSON parsing, pipeline handling, startup diagnostics, and
acceptance resource adjustments consume no product loops.

## Deferred issues

- Plugin compatibility is proved by the focused job flow rather than a
  separately maintained dependency lock.
- Jenkins core and plugin upgrades remain supervised because administrators
  must review the applicable upgrade guide and plugin compatibility.
- Public Postfix delivery is not attempted from local acceptance.
- Docker acceptance does not repeat installer, kernel, or hardware checks.
